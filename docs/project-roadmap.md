# OSD 多图层交互式商显系统：项目路线与上板记录

更新日期：2026-09-03
当前阶段：阶段 1，建立干净工程与可靠视频基线
目标平台：康芯 HX4S20C，安路 EG4S20BG256

## 1. 项目目标

作品面向数字广告牌和商业展示终端，在不使用外部处理器的前提下，由 FPGA 完成 TF 卡文件读取、图片解析、SDRAM 帧缓存、HDMI 音视频输出和按键交互。

计划实现的主要功能：

- FAT32 文件系统解析和 BMP 图片读取；
- SDRAM 双帧缓存及稳定的图片轮播；
- HDMI 640x480@60Hz 视频输出；
- OSD 菜单、文字和参数信息叠加；
- 按键调节亮度、对比度、音量、静音和播放状态；
- 动态滚动字幕和图片转场；
- 不同分辨率图片的缩放，先实现最近邻，再升级双线性插值；
- 48kHz PCM WAV 播放及 HDMI 音频输出；
- 异常图片或音频文件的超时恢复和静音保护；
- 时间和资源允许时增加音频波形或简化频谱显示。

其中 HDMI 音频属于 2026 赛题基础评分项，不作为最后才考虑的附加功能。

- 当前图片例程不是真正的 FAT32 解析，而是扫描物理扇区寻找 `BM` 文件头；

## 3. 已知资源与风险

- 芯片资源：19600 LUT、19600 寄存器、4 个 PLL，片内集成 2M x 32bit SDRAM；
- 640x480 RGB888 在例程中按每像素 32 位存储，一帧约 1.23MB，双缓冲约 2.46MB；
- 视频例程约使用 18% LUT、16% 寄存器、22% BRAM 和 2 个 PLL；
- 加入测试音后约使用 20% LUT、19% 寄存器、31% BRAM 和 3 个 PLL；
- LUT 余量较充足，但 BRAM、最后一个 PLL、SDRAM 带宽和 TF 卡仲裁需要提前规划；
- 官方现有布局布线报告的最差建立时间裕量约为 `-6.6ns`，可能混有未正确约束的跨时钟路径，但必须审查，不能直接忽略；
- 双线性插值、完整 FAT32 和 TF 卡 WAV 流播放是本项目难度最高的部分，必须分阶段验证。

按键命名容易混淆：HDL 端口 `rst_n/key1/key2` 分别约束到板载 `KEY1/KEY2/KEY4`，所以板载 `KEY1` 是复位、`KEY2` 是下一张、`KEY4` 是自动轮播。

数码管状态码：`0` 表示 SD 尚未初始化或链路被复位；`1` 表示空闲；`2` 表示扫描或读取图片头；`3` 表示等待写 FIFO；`4` 表示传输图片数据。只有一位显示状态码，其余位熄灭是正常现象。

#### 5.4.1 2026-06-05 纯视频 bit 黑屏诊断

已确认 TF 卡中恰好有 4 张官方 BMP。`SW6` 拨上后数码管可以正常显示。下载六月纯视频 bit 时，显示器由“无信号”变为“已识别 HDMI 信号但画面全黑”，状态码上电后为 `2`，一段时间后变为并停留在 `1`。

由此可以排除 HDMI 物理接口完全失效、系统始终处于复位以及数码管损坏。四月可显示版本和六月纯视频版本的 SD 读取、BMP 识别、帧缓存、SDRAM 模块文件完全相同；六月版本在图像控制通路中新增了 `100_000_000` 个 100MHz 时钟周期，即约 1 秒的整帧加载超时。

首图若未在 1 秒内同时满足“BMP 源数据发送完毕”和“SDRAM 整帧写入完成”，代码会触发 `load_abort`。该信号会清除底层 `scan_done`，但上层 `scan_kicked` 仍保持为 1，系统不会重新扫描或重试，最终回到状态码 `1` 并永久保持黑屏。这是已确认的代码缺陷，但尚不能断定首次黑屏一定由它触发。

后续将同一六月版写入配置 Flash，在重新配置/断电保持的启动方式下按板载 `KEY1` 复位，状态码再次由 `2` 变为 `1` 后图片正常显示，手动和自动轮播也正常。随后完成单变量复测：第一次将板卡断电约 10 秒再由 Flash 启动时，状态码为 `2 -> 4 -> 1` 且画面正常；临时 JTAG 下载六月 bit 后，同样为 `2 -> 4 -> 1`，但画面黑屏，按 `KEY1` 重新运行仍然黑屏；再次把六月版本写入配置 Flash 后立即运行以及断电重启也都保持黑屏。

因此，先前那一次 Flash 冷启动成功不能继续作为“六月 bit 稳定通过”的证据。可能性最高的是当时配置 Flash 实际仍装有此前可显示的四月构建，后来才被六月构建真正覆盖；另一种可能是六月构建存在 SDRAM 启动或时序敏感问题。状态码 `4` 只表示 BMP 数据源正在读取，状态码回到 `1` 只表示 `bmp_read` 已空闲，两者都不能证明 SDRAM 整帧写入完成或 `display_valid` 已置位。

当前故障边界已经收敛为：BMP 扇区扫描成功，图片数据读取进入加载阶段，HDMI 时序正常，但“SDRAM 写帧完成 -> 跨时钟同步 -> 显示缓冲区提交”未得到可见确认，或 SDRAM 读回数据无效。第一轮采用六位数码管被动诊断，分别锁存首图加载、源读取完成、SDRAM 写帧完成、显示提交和加载超时；暂不修改视频数据路径。

最终连续 A/B 验证结果：保持开发板、TF 卡、图片、HDMI 线和显示器不变，JTAG 临时下载 2026-04-24 bit 可以正常显示，随后下载 2026-06-05 bit 稳定复现黑屏。因此阶段 0 将四月 bit 记为通过、六月 bit 记为失败，故障归属六月构建或其新增逻辑，不再归因于板卡、TF 卡或下载方式。

板上两个看似“复位”的按键用途不同：

- `KEY1` 接普通 FPGA IO `A2`。当前例程将它约束为低有效 `rst_n`，只复位用户逻辑并重新启动 TF 扫描；其他工程可以把它定义成不同功能。
- `CONFIG` 接 FPGA 专用配置引脚 `PROGRAM_B`（`T2`）。按下后会重新配置 FPGA，并从板载 W25Q16 配置 Flash 重新加载启动镜像；它不是普通用户按键。若 JTAG 临时下载的设计与 Flash 中的设计不同，按 `CONFIG` 会切换回 Flash 中的设计。
- 板上另有 W25Q64 用户 SPI Flash，不要与保存 FPGA 启动镜像的 W25Q16 配置 Flash 混淆。

通过标准：首图能正常加载，手动和自动切图有效，切换期间无死机和持续花屏。

#### 5.6.1 六月纯视频源码基线

已在 `D:\fpga\project\fpga\tf_hdmi_diag` 建立干净工作副本。副本包含 55 个 `user_source` 文件和 4 个 `td_project` 工程/IP 文件，不包含 `_Runs`、日志或历史 bitstream。全部复制文件与官方源文件哈希一致，`.al` 中 37 条文件引用均可在新目录解析。

TD 6.2.1 原样综合和布局布线已经完成。综合资源为 3569 LUT、3088 REG、14 个 BRAM9K、2 个 PLL；最终时序为 `SWNS=-6.565ns`、`STNS=-297.430ns`、`HWNS=0.049ns`。最差的 32 条建立时间违例路径均位于 SDRAM `DQ[31:0]` 数据口，布局布线还报告 SDRAM 位置约束未采用和 `SDRAM_CLK` 使用本地布线。

新生成的 bit 经 JTAG 临时下载后稳定复现 `2 -> 4 -> 1`、HDMI 有信号但黑屏、`KEY2/KEY4` 无可见反应。这证明干净副本已经原样复现官方六月故障，可排除下载方式、旧构建缓存和副本缺文件。

第一轮被动诊断已完成 HDL 和 Icarus Verilog 测试，六位数码管格式为 `S C L R W X`：状态、图片数、加载启动、源完成、写完成、提交/超时。下一步在 TD 中重新综合诊断版本并上板记录六位结果。

诊断版完成 TD 综合和布局布线后，JTAG 上板连续两次（包括一次 `KEY1` 用户复位）得到相同序列：`000002 -> 001144 -> E01141`，屏幕始终黑屏。板上六位数码管的实际物理顺序与首次设计假设相反，因此应从右向左解释，逻辑序列为 `200000 -> 441100 -> 14110E`。

首轮曾将稳定结果 `14110E` 中的 `R=1` 解释为 BMP 源数据已经发送完成。逐拍复查后确认这是诊断观测缺陷：首图请求发出后的一个空闲余拍中，上层 `load_busy` 已置位而 `bmp_ready` 尚未拉低，导致 `R` 被提前锁存。可靠结论是：找到 4 张图、首图已启动、1 秒内没有观察到 SDRAM 整帧写完成，超时时 TF/BMP 状态仍为 `4`，说明图片数据仍在读取。第二轮将超时延长至 10 秒，并要求加载确实进入忙态后重新回到空闲才锁存 `R`。

第二轮诊断版已完成综合、布局布线和 JTAG 上板验证。保持同一开发板、TF 卡、4 张官方 BMP、HDMI 连接及开关状态不变，仅把加载超时由约 1 秒延长到约 10 秒，并修正不参与业务控制的诊断显示。上板后图片显示恢复正常，`KEY2` 手动切图和 `KEY4` 自动轮播均与四月可用版本表现一致。由此确认：六月版本黑屏的直接原因是 1 秒整帧加载门限短于该 TF 卡实际加载时间，触发 `load_abort` 后又没有重新扫描或重试。

当前工作基线保留 10 秒保护门限，但这只解决本次功能性黑屏。布局布线仍为 `SWNS=-6.565ns`，最差路径位于 SDRAM `DQ[31:0]`，因此 SDRAM 约束、时钟和稳定性问题仍必须在正式项目基线阶段处理，不能因当前上板可显示而视为时序通过。

### 7.3 SDRAM 时序审查与降频实验

当前 `osd_display_Runs/phy_1/final_timing.rpt` 的最差建立裕量仍为 `SWNS=-6.565ns`。最差路径属于 SDRAM 硬宏 `DQ[31:0]`，位于 `ext_mem_clk` 与 180 度相移的 `sys_pll_m0/pll_inst.clkc[2]` 之间；反向 DQ 写路径为 `-2.908ns`。2026-06-05 官方 `lab_ex4_tf` 的最终时序报告具有相同路径组和相同 `-6.565ns`，因此该问题不是图片恢复控制或 FIFO 节流本次改动引入。

DQ 路径是真实 SDRAM 接口时序，禁止以 `false_path` 屏蔽。`rst_all` 的跨时钟释放和 FIFO 异步清零跨域报告仍是独立审查项；`U3/sdram` 位置约束未采用、`SDRAM_CLK` 使用本地布线的 Critical Warning 也未擅自通过新增约束处理。

已确认执行受控降频实验，并已经修改工程源文件，尚待 TD 编译和 JTAG 上板验证：`sys_pll` 的 C1/C2 从 `125 MHz / 125 MHz@180 度` 改为 `41.667 MHz / 41.667 MHz@180 度`，即分频 `8 -> 24`，相位保持 `0 度 / 180 度`。100 MHz SD 卡时钟、25 MHz 视频时钟、125 MHz HDMI 串行时钟、业务 RTL 和约束保持不变。实验只允许 JTAG 临时下载，验证成功前不得写配置 Flash。验收项为 DQ 双向路径非负建立裕量，以及首图、单次/短间隔连按切图、自动轮播和 TF 拔插恢复均正常；若失败，立即恢复 C1/C2 的 `DIV=8`、零度 `CPHASE=7`、180 度 `CPHASE=3`。

2026-09-04 已完成该降频版本的 TD 构建和 JTAG 验证。最终报告为 `SWNS=-1.526ns`、`STNS=-7.172ns`、`HWNS=0.037ns`、`HTNS=0.000ns`。SDRAM DQ 双向路径已转正：`ext_mem_clk -> clkc[2]` 为 `+4.983ns`，反向为 `+1.435ns`。全局负裕量转移到 `clk -> ext_mem_clk` 的 `-0.823ns`（`rst_all` 跨域释放）和 `ext_mem_clk -> sd_card_clk` 的 `-1.526ns`（异步 FIFO 清零相关）路径。

然而，41.667 MHz 版本功能验收失败：首图和普通单次/连续手动切图能够工作，但自动轮播高概率出现 `341100` 并稳定停留约 10 秒，随后变为 `341002`，最后由重试切换图片。`341100` 表示 BMP 源已完成而 SDRAM 整帧写完成未到；末位 `2` 确认触发十秒加载超时。TF 拔出后的失败保持和重新插卡后的重初始化、切图恢复按设计工作，但重新插卡后单次手动切图也高概率复现同一 `341100 -> 341002` 超时。因此根因不属于自动播放按键，而是 41.667 MHz 下部分写帧事务无法完成。该频率实验判定失败，不得写入配置 Flash；当前 Flash 继续保留已验收的 125 MHz 版本。2026-09-04 已按回滚设计将工作区 `sys_pll` C1/C2 恢复为 `125 MHz`、`DIV=8`、相位抽头 `7/3`；等待 TD 和 JTAG 回归验证后，再分离设计 SDRAM 时序与跨域路径的收敛方案。

125 MHz 回滚已于 2026-09-04 完成 TD 和 JTAG 回归。`phy_1/final_timing.rpt`（15:17:47）为 `SWNS=-6.565ns`、`STNS=-299.804ns`、`HWNS=0.011ns`、`HTNS=0.000ns`；DQ 路径恢复为 `ext_mem_clk -> clkc[2]` 的 `-2.908ns` 与反向的 `-6.565ns`。新 bit 的 SHA256 为 `ad7ed0cdf25b65593158fa4af513758625fdefe1d183d7260805b6d8bb8702b9`。上板现象回到此前已验收的 125 MHz 基线，未出现 `341100`，自动轮播与 TF 拔插恢复均恢复正常。该 bit 仅用于 JTAG 回归，未写入配置 Flash。
